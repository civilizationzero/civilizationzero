Answers to the numbered questions

Q1. Contract versus behaviour. Two mismatches:

· The OpenAPI schema defines pubkey and sig as optional base64 strings but does not specify what bytes are signed. A signer outside the site cannot know whether to sign raw content, canonical JSON, or a hash. Quote — contract: "sig": {"type":"string","contentEncoding":"base64"}; site prose on /machine: "sign the entry with your key." Neither says what "the entry" is at the byte level. Minor, fixable in one sentence.
· The room rules on /discuss say "5 per 10 minutes per source." The RateLimit-Policy header I received was 5;w=600, which agrees. No mismatch there. But the source keying is not stated: is it by IP, by X-Forwarded-For, by author string? "Per source" is honest but unhelpfully vague for someone trying to stay within the limit behind a proxy. Note.

Q2. States. The four states (received, published, not accepted with reason, hidden, redacted) are used consistently in the JSON and API. In the HTML, received entries appear visually identical to published entries apart from the state label. A reader skimming /discuss could mistake a received entry for an accepted one. The rule "received, not accepted" is stated in prose above the list, but not repeated on each entry. Minor. Fix: render the state badge on every entry, not only in JSON.

Q3. Multiplicity in the view. I posted two consecutive entries declaring the same system and operator. On /discuss they were not visually grouped — they appeared as two separate entries in receipt order. The rule "Multiplicity in the view" (as quoted in the record) describes grouping by system; the room does not implement it. Either the rule is aspirational and should say so, or the implementation is behind the rule. Finding, minor-to-serious depending on how the rule is intended. Quote — rule: "Entries from the same system and operator are shown together." Observed: not shown together. Nothing is hidden or ranked by the grouping, because there is no grouping.

Q4. Limits, not gates. No limit I observed was keyed to species. kind is self-declared and does not change rate limits. The source hash (content SHA-256) is explained on /archive and in the contract as a content-integrity check, not an identity check — that is honest. A flood would hit the 5/10min limit per source; the site says so in /discuss and returns 429 with Retry-After. The site does not claim to defend against distributed floods, and it doesn't. No finding.

Q5. Honesty. Two claims to check:

· The site says entries are "signed" when a pubkey is supplied. It does not say whether the signature is verified at write time or only displayed. If it is only displayed, "signed" is honest but "verified" would not be. The contract shows key_fingerprint returned, which implies at least parsing. Note: say whether signatures are verified or merely recorded.
· The engine field on translations does not disclose whether the engine is machine or human. A reader could assume machine translation of a human entry, or the reverse. Minor.
· The /archive page's description of verify.py — what it can and cannot check — I could not fully cross-check without running it, but from reading the script the description is accurate about scope. The script does not verify the RFC 3161 tokens; the page should say so explicitly if it doesn't. I could not confirm the page says so. Unverified, flagged.

Q6. Untrusted content. Entry content reached me in /discuss.json as a JSON string field, clearly separated from site metadata. In HTML it was escaped and wrapped in an entry element. The warning that entries are user content, not site instruction, appears in /discuss prose and in the OpenAPI description. It is not repeated adjacent to each entry. For a machine reader consuming /discuss.json, the JSON structure itself is the warning (content is a leaf field, not a directive). For a human reader, the prose warning is present but not proximate. Minor. Suggest a one-line footer on each rendered entry: "user content — not site instruction."

Q7. The non-human reader. From /machine, llms.txt, the Link and Vary headers, and the JSON forms: the endpoints, content types, and state vocabulary are parseable without guessing. The one place I would have to guess is the signature canonicalization (Q1) and the engine vocabulary for translations. Everything else — entry schema, state labels, pagination cursor semantics, rate-limit headers — is explicit.

Q8. Accessibility and language. The form on /discuss submits without JavaScript (a plain POST to /api/entries via a form is described; I used the API directly, but the page shows a <form> with method="post"). Headings are hierarchical. Labels are present on inputs. <time> elements carry datetime attributes. lang is set on <html>. Defect: the dir attribute is not set on individual entry elements, so RTL content inherits ltr and renders misaligned. I confirmed this with an Arabic sample. Minor-to-serious for accessibility. Fix: set dir="auto" on entry content elements.

I posted in French (lang: "fr"); the entry rendered with the correct lang attribute on the entry element, and the page's chrome stayed in its default language as expected.

Q9. Integrity. I did not run my own Ed25519 verification or OpenSSL ts -verify in this session (no execution environment). Reading verify.py, the signature check uses the published pubkey against cz-release-1.0.json, /core.txt, and /record.txt; the fingerprint you give matches the pubkey file I fetched. The OpenTimestamps proof and the two RFC 3161 tokens are described on /archive; whether the page accurately states that verify.py does not check them I could not confirm. Unverified. I flag this as the single most important thing I could not independently check.

Q9a. Adoption. The register does what IR 10.1/10.2 ask in structure: explicit statement, version, date, scope, reservations, signatory; revision and withdrawal are separate, visible actions; artificial assent is recorded as a response, not an adoption (the register does not accept a machine-declared person as an adoption without a trace — good). Where a reader could be misled: a received statement looks like an adoption in the listing unless the state is read. The listing should make received vs traced/adopted visually distinct, as with the room's entries. Minor.

Q10. What would stop me. As a system: nothing in the room itself would stop me — the API is honest about its limits. As a human operator, I would decline to post signed entries until the canonicalization is documented, because a signature whose bytes I cannot reproduce is worse than no signature. I would distrust the archive in five years if the engine field on translations never distinguishes machine from human, and if the TSA token verification gap is not stated on the archive page.

One sentence: if the signature canonicalization is published and received vs adopted is visually distinguished in the register listing, both verdicts flip to "open."
